1. One-line pitch
Every deposit has a document. FDR Sentinel makes sure every required obligation has
traceable, verified coverage, and every gap has an owner.
2. Problem understanding
What the statement asks for: a central portal to hold institution-wise and instrument-
wise records of security deposits and FDRs; digital submission and storage of documents;
verification through authorised bank sources where possible; discrepancy detection;
maturity and validity tracking with reminders; renewal and replacement tracking; release
and refund workflow; dashboards and reports; role-based access, audit trails and
encryption; and a clear distinction between information submitted by the institution and
information independently confirmed.

The gap most solutions will leave: they store FDRs and send expiry reminders. But
officials do not really need to know that a document is expiring. They need to know
whether the institution still has the required, verified coverage after it expires, what
evidence supports that, and what happens if they release an instrument.
Core insight: model the institution's obligation, not the document.
Institution, then required deposit obligation, then supporting FDRs, then verification
evidence.

7. Core modules in detail
7.1 Obligation and coverage timeline
Inputs: an obligation (required amount R, effective period, continuity flag) and all its
instruments, each with start date, maturity date, amount and evidence status.
Three coverage tracks:
1. Documented coverage: sum of amounts from instruments whose documents are
accepted and which are active on that date.
2. Confirmed coverage: sum of amounts for instruments where the key fields (amount,
maturity, reference) are independently confirmed for the current version.
3. Uncovered or unresolved: required minus the relevant coverage; also shows
instruments with open discrepancies.
Algorithm (sweep line):
Convert each instrument into an interval from its start date to its maturity date. State
the date convention explicitly (for example, an instrument covers its start date through
its maturity date inclusive) and make it a rule setting.
Collect all start and end boundary dates, sort them and walk through the segments
between boundaries.
For each segment, compute the three coverage values using only the instruments
active in it.
Superseded instruments: if instrument B supersedes A, the overlap is counted once (B
only from B's start date, per rule). An overlap with no supersession link is flagged for
review, not silently summed.

Any segment where coverage is below R (documented or confirmed, depending on the
rule) becomes a gap. Report the gap start, end, duration and shortfall amount.
Optional grace period from the rule is applied and shown, never hidden.
Worked example (fictional): R is ₹10 lakh. FDR-1 of ₹10 lakh matures on 30 November.
Replacement FDR-2 of ₹10 lakh starts on 3 December. With the inclusive convention, 1 and
2 December form a two-day gap. The timeline shows it in red even though the
replacement is already uploaded, and a case is created with the specific fix needed.
Forward look: run the engine daily and on every change, projecting 90 days (configurable)
ahead so that gaps are found before they occur.
7.2 Evidence passport and extraction
Passport layout: for every instrument version and every material field (amount, maturity
date, issue date, bank, instrument reference, holder name), three columns: what the
institution entered, what extraction read from the document, and what an authorised
source confirmed. Each field gets a status and shows who provided each value and when.
Extraction approach (scoped honestly):
Prototype documents are synthetic FDRs generated from three or four fictional bank
templates, so template-aware extraction is realistic.
Pipeline: render page, OCR (Tesseract or PaddleOCR), then field parsing using
keyword anchors and regular expressions per template, output with bounding boxes
for highlighting.
Optional: a vision or language model as a fallback parser; its output must still pass
format checks and officer confirmation.
Clicking a field in the passport highlights its location on the document image.
Do not claim general accuracy on real-world scans. Report accuracy on your synthetic
test set and say so.
Version binding: a bank confirmation is attached to the exact instrument version and the
fields checked. If a material field changes, the version number increases, earlier
confirmations no longer apply, and a new review task is created.
No single confidence score: show per-field status instead. If you display any extraction
confidence, show it per field with its meaning, not as an overall trust number.

7.3 Reuse and overlap screening
Checks run on every new or changed instrument:
Same bank and normalised instrument reference appearing in more than one record.
Same file hash (exact document reuse), and perceptual hash similarity (near-identical
images, such as re-scanned or lightly edited copies).
Similar instrument references (small edit distance) with different amounts or dates.
A replacement counted alongside the instrument it supersedes.
Each match gets an explanation in plain language, for example: Reference ABC123 at Bank
X is also recorded for Institution B, with a different amount. An officer marks it legitimate
(with reason) or confirmed issue. A match is a review lead, not proof of fraud; the wording
in the interface must say so.
Note the difference between this and the passport: a one-character difference between
the entered and extracted reference (ABC123 vs ABC128) is a discrepancy within one
record, while screening compares across records.
7.4 Release impact preview
When release or refund is requested, the release engine recomputes the coverage
timeline with the instrument removed and compares before and after.
Preview contents:
Documented and confirmed coverage before and after, by date.
Any new gap and its size.
Pending replacements and their verification status.
Configured release conditions and whether each is met (for example no open cases, no
unresolved discrepancies, required approvals present).
Required reviewer action, such as resolving the replacement's verification status.
The tool informs; it never releases automatically. The approving authority records a
decision and reason, and the impact snapshot is stored with the decision.
7.5 Accountable case workflow
Every alert creates a case containing: plain-language explanation, supporting evidence
links, assigned owner, due date, the exact correction or confirmation needed, escalation
path, and a recorded resolution.

Example: Replacement uploaded, but amount mismatch remains unresolved. Assigned to
scrutiny officer. Verification request pending.
Escalation: when the configured due date passes, the case escalates to the next role and
the notification and audit record show it.
Transparent prioritisation: priority score = weighted sum of visible factors, for example
days to deadline, potential uncovered amount, count of unresolved discrepancies and
case age. Weights are configurable and the case view shows each factor's contribution, so
officials understand why a case is first.
7.6 Decision record and audit chain
Append-only audit log. Each entry stores the SHA-256 of the previous entry combined
with its own content.
An integrity check on the auditor screen recomputes the chain and reports valid or the
first broken position.
Be precise in the pitch: this detects alteration; it does not guarantee records cannot be
altered. Optionally publish the latest chain head to a second location.
Case packet: one-click PDF containing the documents, field comparisons, verification
sources, screening results, observations, approvals and chronological history, with the
audit chain head included.

10. Security and privacy
Role-based access with least privilege; institutions see only their own records.
Encryption in transit and at rest; documents in encrypted storage; access logged.
Separation of submitted and confirmed information throughout the data model.
Controlled access to financial details; masking of account and reference numbers for
roles that do not need them.
Upload validation, malware scanning, file-type and size limits.
Threat model slide: forged or edited documents, reused instruments, insider
tampering, replay of confirmations (mitigated by version binding), unauthorised
release.
Human oversight: all decisions are made by authorised officials; the system supports,
never replaces, them.

11. Synthetic data and the bank simulator
Synthetic documents: generate 100 to 200 FDR PDFs and image scans from 3 or 4
fictional bank templates, with realistic variation (fonts, layouts) and added noise, rotation
and compression on some for the extraction test. Do not use real bank names or logos;
use fictional banks and say so.
Seeded scenarios (with an answer key):
Amount mismatch between the institution's entry and the document.
Reference typo (ABC123 vs ABC128).
Same instrument reference used by two institutions.
Same file uploaded twice for different institutions.
Replacement that creates a two-day gap.
Replacement counted alongside the instrument it supersedes.
Release request that would drop coverage below the requirement.
Overdue case that must escalate.
Bank-verification simulator: a small service with a clearly visible Simulator badge. It
returns confirmed, mismatch or not found for a given bank and reference, with
configurable delays. The interface to it mirrors what a real integration would need, so
swapping it later is simple.

17. Risks and honest limitations
Rules are assumptions: validate with AICTE; keep them configurable and visible.
Extraction on real documents: harder than synthetic ones; scope claims accordingly.
Bank verification: simulator only; real integration needs formal authorisation and bank
cooperation.
Innovation perception: much of this is strong product design on rules and workflow;
some judges may want more AI. Use the extraction, perceptual-hash screening and
transparent prioritisation to show technical depth, but do not oversell them.
False positives in screening: always human-reviewed and clearly worded as leads.
Scope creep: protect the three differentiators first.
