1. One-line pitch
AcadTrust turns every AICTE-approved institution's student data into a signed, consent-
controlled, tamper-evident record linked to the student's APAAR ID, so AICTE can detect
excess or duplicate enrolment automatically and employers can verify a student in
seconds without calling the college.
2. Problem understanding
What the statement says. PGDM institutions submit student-level data yearly, but most
other AICTE-approved institutions only report total enrolment during approval. AICTE
therefore cannot verify who is actually enrolled. APAAR ID (the national academic
identity) can be the unique key.
What is actually hard (the real gaps):
1. Trust: a CSV upload only proves what the institution claims. Nothing proves the record
is genuine or unaltered later.

7. Core modules in detail
7.1 Ingestion and rule-based validation
Checks run per row and per institution:
APAAR ID format and checksum rules (12 digits; confirm exact format against official
guidance); missing or invalid IDs rejected with reason.
APAAR existence check against the mock service (in production, the official service).
Duplicate APAAR ID within the same upload.
Enrolment greater than approved intake, computed per programme and per year;
supernumerary seats treated separately according to the approved rules.
Category consistency: for example, a student flagged both OCI and foreign national, or
NRI with inconsistent supporting fields.
Required fields present; date logic (admission date before graduation date; age
plausibility).
Programme must exist in the institution's approved programme list.
Output: an accepted set, a rejected set with row-level reasons, and a downloadable error
report so institutions can fix and resubmit quickly.
7.2 Privacy-preserving duplicate enrolment detection
Goal: find a student enrolled at two institutions in the same period without AICTE
analysts handling raw IDs.
Method: compute apaar_hash = HMAC-SHA256(secret_key, APAAR_ID). Matching runs
only on these hashes. Same hash at two institutions with overlapping active periods
creates a duplicate flag.
Important detail (and a point judges may probe): a plain hash of a 12-digit number can be
brute-forced, so use a keyed hash (HMAC) with the key held in a secrets manager or HSM.
The raw ID stays encrypted in the vault.
Fuzzy cases: when APAAR is missing or doubtful, a secondary match uses normalised
name, date of birth and guardian name with similarity scoring; such matches are lower
confidence and always routed to human review.
Human in the loop: a flag is a prompt for review, never an automatic penalty.

7.3 Explainable anomaly detection
Three detector types, combined into one risk score per institution-programme:
1. Rules: enrolment over intake; unexpected jump in supernumerary, NRI, OCI or foreign-
national counts.
2. Statistics: compare each institution against its own history and against peer
institutions (same programme, state, size band) using robust z-scores or median
absolute deviation; flag sharp year-over-year changes.
3. ML (optional, only if time allows): Isolation Forest on the numeric feature set for
unknown patterns.
Explainability: every flag carries reason codes and the numbers behind them, for
example: Enrolment 312 vs approved intake 240 (130 percent); NRI share 4.1x its three-
year average; 18 students share hashes with another institution. The dashboard shows
these reasons in plain language. No black-box score is shown without them.
7.4 Verifiable student credentials
On accepted data, the credential service builds a minimal payload: credential_id,
institution_id, programme, admission year, status, and the apaar_hash (not the raw ID).
It signs the payload with Ed25519; keys are rotated and identified by key_id. The
structure follows the W3C Verifiable Credentials idea so it is standards-aligned.
A QR code carries a short verification URL plus the credential_id. Scanning it calls the
verification service, which checks the signature, expiry, revocation and the student's
consent, and returns verified or not verified with only the consented fields.
Revocation: if a record is corrected, withdrawn or found fraudulent, the credential is
revoked and verification fails immediately.
Certificates: the QR and APAAR ID can be printed on certificates issued by degree-
awarding bodies, as the statement requires (requirement 10). Provide a printable
certificate footer template.
7.5 Student consent ledger
A student logs in (mock login in the prototype; the real design would use an existing
national identity or APAAR authentication route) and sees who can verify their record.
They approve verifier categories (for example a named employer) and which fields are
shared, with an expiry.

Revoking consent takes effect immediately; the verification service checks consent on
every request.
Every verification attempt is logged and visible to the student.
Design aligns with the principles of India's Digital Personal Data Protection Act, 2023:
purpose limitation, data minimisation, consent and the right to withdraw. State this as
alignment, not as certified compliance.
7.6 Tamper-evident audit trail
Every significant action (upload, validation result, flag raised or cleared, credential
issued or revoked, consent granted or revoked, verification) is appended to the
audit_chain.
entry_hash = SHA-256(prev_hash + serialised entry). Changing any past entry breaks
every later hash.
A one-click integrity check on the auditor screen recomputes the chain and reports
valid or the first broken position.
Optional extra: publish the latest chain head hash periodically to a second location, so
even an administrator cannot silently rewrite history.

Institution view: intake vs enrolment per programme, validation status, open flags,

National view: total enrolment, utilisation of approved intake, quota-category trends,

Reports: institution compliance report, regional summary, policy brief with trends;

Real-time: use WebSocket or short polling so new uploads and flags appear without

9. Security and privacy design
Authentication and RBAC with least privilege; separate roles for institution, regional
officer, senior management, auditor and verifier.
Encryption in transit (TLS) and at rest (database and object storage); raw APAAR IDs
only in the vault.
Data minimisation: analytics and matching use hashes and aggregates; verifiers only
see consented fields.
Secrets and signing keys held in a secrets manager (for the demo, environment
variables with a clear note that production uses an HSM or KMS).
Rate limiting and anomaly alerts on the verification endpoint to block scraping.
Input validation and upload scanning; row-level audit of who changed what.
Threat model slide: insider misuse, forged uploads, replay of QR codes (mitigated by
expiry and server-side checks), enumeration attacks on the verification URL
(mitigated by random credential IDs and rate limits).
